# Технический аудит SlideOverTahoe — 09.09.2026

## Итог

Основа подходит для небольшой macOS-утилиты: SwiftUI + AppKit + публичный Accessibility API, без сторонних зависимостей. Полное переписывание не требуется. Текущая реализация — прототип с существенными ошибками жизненного цикла окна; для повседневного использования сначала нужно обеспечить надёжный возврат окна.

Главное расхождение с концепцией: пользователь должен выбирать **окно**, но рабочие настройки выбирают **приложение**, а код берёт focused/first window. Старый `WindowPickerView` существует, но не используется в рабочем интерфейсе.

Debug и Release собираются, `xcodebuild analyze` проходит. В добавленных проверках реального менеджера с подменой AX: **3/12 PASS, 9 FAIL**. Это девять неуспешных сценариев, часть которых связана общей причиной. Подтверждённой удалённо эксплуатируемой уязвимости не найдено; есть ошибки доступности/целостности управления окнами и недостатки подготовки к выпуску.

### Причины и необходимые исправления

**A01/A04:** `hide()` безусловно читает текущий AX frame. Проверка `!isAnimatingMove` добавлена в периодическую синхронизацию, но не в `hide()`. Сохранять видимый frame только в устойчивом visible-состоянии; повторный hide сделать идемпотентным. Цель возврата должна переживать смену направления анимации.

**A02:** `dock()` перезаписывает `state`, не восстановив предыдущую цель. Рабочий `EdgeController` при выборе другого приложения вызывает этот путь. Восстановление старой цели должно завершиться успешно либо оставить явно доступный механизм повторного восстановления; только затем переходить к новой.

**A03:** token инвалидируется при конкурирующем animated move, однако ветка `!animated` выполняется раньше и ничего не отменяет. `restoreAndClear()` использует именно её. Инвалидировать все незавершённые движения до любого нового позиционирования, в том числе restore/disable/смены цели. Завершение анимации проверяет session ID и актуальное состояние.

**A05/A08:** `AXUIElementSetAttributeValue` возвращает результат, но приложение его игнорирует. Нужен типизированный AX-клиент; изменение состояния по подтверждённому результату и, при необходимости, readback фактического положения. При невозможности восстановления сохранить безопасный frame, показать понятную ошибку и разрешить повторить возврат. Не зацикливать retries.

**A06/A07:** проверять настройки при декодировании и перед применением, использовать один источник геометрических параметров. Нижнее ограничение через `max` в `EdgeController` не заменяет проверку верхних границ и задержек. При смене grip пересчитать скрытую позицию и расположение индикатора.

**A09:** `updateSettings()` не отменяет таймеры, а `startInactivityMonitoring()` сразу выходит, если observers уже есть. Обновление настроек должно отменять/перепланировать соответствующие действия. Callback повторно проверяет текущую настройку, видимость, активное приложение, курсор и session ID. Аналогичный недостаток есть у таймера ухода курсора: переключатель проверяется при планировании, но не перед выполнением.

## 3. Дефекты и риски по анализу кода

Следующие выводы основаны на изучении путей исполнения; реальная GUI-матрица для них ещё не выполнена.

### B01 — выбор и жизненный цикл конкретного окна, P1

`SettingsView.swift:31–43` выбирает bundle ID; `AXWindowResolver.swift:47–64` — focused/first window. `EdgeController.swift:92–100` считает совпадение PID достаточным и не проверяет, существует ли прежнее окно. При закрытии окна без завершения приложения, смене активного документа или создании нового окна менеджер может продолжать работать с недействительным AX element.

При запуске приложения уведомление `didLaunchApplication` может прийти до создания его окна. Если resolve вернёт nil, повторного ожидания window-created нет; привязка может не возникнуть до следующего применения настроек/события другого приложения. Выдача Accessibility после старта тоже не запускает явный retry привязки сохранённой цели.

Подключить выбор конкретного окна; проверять role/subrole, доступность изменения позиции и жизненный цикл. Для запоздалого создания окна использовать observer или ограниченный retry. Старый resolver по ближайшему центру (`AXWindowResolver.swift:29–44`) не имеет порога/проверки размера и при неоднозначности способен выбрать другое окно; это пока риск неиспользуемого UI-пути, а не подтверждённое поведение рабочего picker.

### B02 — координаты и мониторы, P1

`screenForPoint()` сравнивает AX-центр с `NSScreen.frame`, хотя эти пространства требуют преобразования. `isMouseOverTargetWindow()` принимает как raw frame, так и перевёрнутый frame: получается две области, одна из которых может быть ложной. `normalizeWindowFrame()` индикатора сначала принимает raw frame, если центр попал в screen frame, что не доказывает совпадение координат.

Пример на основном экране высотой 900: AX frame `(100,100,400,300)` соответствует AppKit y=500. Raw-центр при этом тоже лежит внутри экрана, поэтому эвристика индикатора принимает y=100. Это арифметический контрпример по коду, не снятый GUI-тест.

Для глобальных AX→AppKit координат нужен явный flip относительно верхней границы основного дисплея: `appKitY = primaryScreenMaxY - axY - height`. Использовать основной дисплей координатной системы, а не меняющийся `NSScreen.main` и не верхнюю границу произвольного второго экрана. Проверить отрицательные origins и вертикальные расположения дисплеев.

Кроме того, `EdgeController.swift:94–99, 113–121` определяет экран **после hide**, используя центр уже вынесенного окна. Центр может оказаться на соседнем дисплее или вне всех экранов; fallback на `NSScreen.main!` размещает overlay в неверном месте. Последующие перемещения/изменения экранов не синхронизируют панели с менеджером: нет наблюдения `didChangeScreenParametersNotification`.

Если справа находится другой монитор, текущая формула переместит окно на него, а не за внешнюю границу рабочего стола. Нужна явная продуктовая политика: поддерживать только внешние края, выбирать внешний край всей конфигурации или использовать другой механизм. Не обещать скрытие на внутренней границе без интеграционного исследования.

Обоснование систем координат: [Apple: kAXPositionAttribute](https://developer.apple.com/documentation/applicationservices/kaxpositionattribute), [Apple: Coordinate system](https://developer.apple.com/library/archive/documentation/General/Conceptual/Devpedia-CocoaApp/CoordinateSystem.html).

### B03 — отложенное раскрытие переживает изменение намерения, P2

`EdgeController.swift:146–159` отменяет revealWorkItem только при следующем планировании. Выход курсора из края не подключён к отмене, `apply(settings:)` не отменяет старую работу. Сценарий: коснуться края с задержкой, уйти — окно позже раскрывается. Сменить цель до дедлайна — callback обращается к уже новому `manager.state`.

`SlideOverManager.swift:271–272` также планирует show через 0.12 с без отмены и без проверки, осталось ли целевое приложение активным. Возможно позднее раскрытие/захват фокуса после нового действия пользователя. Централизовать отмену, проверить актуальные условия в callback.

### B04 — скрытие по неактивности, P2

Таймер неактивности не перепроверяет положение курсора перед выполнением. Если курсор был над окном в момент смены приложения, таймер вообще не ставится; при последующем уходе курсора, когда hide-on-cursor-leave выключен, повторной оценки неактивности нет. Поведение зависит от порядка событий, а не только от настроек.

`hide()` не отменяет inactiveHideTimer. Скрытие по уходу курсора может быть выполнено первым, а запоздалое скрытие по неактивности повторяет hide и вызывает A01.

### B05 — fullscreen, Spaces и недоступные окна, P2

Нет проверки fullscreen/minimized/movable, подтверждения того, что macOS или конкретное приложение действительно разрешило вынести окно за экран. Overlay имеет `.canJoinAllSpaces` и `.fullScreenAuxiliary`, но это не переносит туда целевое окно. Эти флаги нельзя считать доказательством поддержки Spaces/fullscreen/Stage Manager. Нужны capability checks, состояние unavailable и реальные испытания.

### B06 — область ввода и состояние индикатора, P2

Прозрачная панель вдоль всей высоты экрана имеет `ignoresMouseEvents = false` и существует также при раскрытом окне. Она может перехватывать клики/drag у правого края, включая scrollbar и resize. Требуется GUI-проверка hit testing и решение о pass-through либо ограничении области.

В ветке обновления того же PID `EdgeController.apply()` не скрывает и не перестраивает уже открытый индикатор. Его callback не проверяет актуальную hidden-сессию. Global mouse monitor не получает события собственной утилиты, а локальный монитор отсутствует; скрытие/появление индикатора около собственных панелей требует проверки. Нет клавиатурного способа раскрыть ручку и accessibility-семантики её действия.

### B07 — восстановление после аварии, P1 как ограничение надёжности

`applicationWillTerminate` и `deinit` помогают при штатном жизненном цикле, но не гарантируются при crash/force quit. Исходный frame хранится только в памяти. После повторного запуска resolve может получить уже сдвинутое окно и запомнить его как исходное. Нужна отдельная стратегия: безопасный ограниченный журнал восстановления с проверкой личности окна либо явная команда возврата на доступный дисплей. Не перемещать произвольное «похожее» окно только по старому PID.

### B08 — подавление активации после завершения чужого приложения, P2

`shouldSuppressRevealAfterTermination()` подавляет раскрытие в течение 1.5 с после завершения **любого** другого приложения. Это эвристика против нежелательной автоактивации, но она может подавить и настоящий клик пользователя в Dock. `lastActivatedPID` записывается, но не читается для принятия решения. Проверить разные причины активации и сформулировать правило поведения; не увеличивать таймаут без проверки.

| Сохранённый PID | Миграция может связать старый PID с другим процессом после перезапуска | PID использовать только внутри текущей сессии; legacy migration делать с осторожной проверкой, при неоднозначности — повторный выбор |

Apple описывает ошибки операции в [AXUIElementSetAttributeValue](https://developer.apple.com/documentation/applicationservices/1460434-axuielementsetattributevalue). Для notarization требуется Hardened Runtime: [Apple: Hardened Runtime](https://developer.apple.com/documentation/security/hardened-runtime), [подготовка приложения к распространению](https://developer.apple.com/documentation/Xcode/preparing-your-app-for-distribution). Отсутствие Sandbox и отсутствие Hardened Runtime — разные свойства.

Не найдено оснований утверждать наличие RCE, утечки по сети, вредоносного кода или обхода системных разрешений. Это ограниченный аудит исходников и сборки, не сертификация безопасности.

## 5. Насколько реализация оптимальна

Для MVP стек и объём кода разумны. Главные проблемы сейчас — порядок переходов состояния и лишние межпроцессные вызовы, а не сложность алгоритмов или расход памяти на SwiftUI.

| Сейчас | Предложение | Ожидаемый эффект/ограничение |
| --- | --- | --- |
| `mouseMoved → isMouseOverTargetWindow → getFrame`: два синхронных AX чтения на каждое событие | Hit testing по кешу; обновление frame через AXObserver + ограниченный fallback | Убрать AX IPC из горячего пути мыши. Например, при 120 доставленных событиях/с сейчас это 240 чтений/с, без учёта таймера; это расчёт по коду, не замер |
| Frame timer раз в 0.4 с, два чтения | AX moved/resized/destroyed notifications, периодический fallback только при необходимости | Сейчас около 5 AX чтений/с на видимое окно даже без движения; скрытый timer уже корректно остановлен |
| Монитор курсора запускается независимо от переключателя hide-on-leave | Подписки по фактическим потребностям; локальные события собственной утилиты при необходимости | Меньше работы и более полное покрытие событий |
| 14 `asyncAfter` на 0.20 с | Одна отменяемая анимационная сессия, время по monotonic clock, последняя цель имеет приоритет | Сейчас примерно 70 команд/с во время движения, без синхронизации с дисплеем; поздние callbacks могут идти пачкой. Не обещать 60/120 fps через AX |
| AX выполняется на main actor, нет явного timeout | Ограничить AX messaging timeout и частоту запросов; затем по замерам рассмотреть отдельного сериализованного исполнителя | Зависшее приложение не должно надолго тормозить меню/настройки. Нельзя бездумно отправить AppKit и manager state на background queue |
| Любое изменение настроек пересоздаёт edge NSPanel; launch/terminate любого приложения вызывает apply | Сравнивать effective settings, обновлять panel frame без пересоздания; фильтровать релевантные события | Меньше churn, исчезновений overlay и повторной работы |
| Первичное apply вручную плюс первое значение `$right` | Оставить один определённый путь инициализации | Убрать дублирование, упростить порядок событий |
| Старый WindowPicker и остатки левого UI в сборке | Подключить и доработать picker по продуктовой задаче либо явно убрать после решения; подчистить неиспользуемые поля | Меньше двух конкурирующих путей управления окном |

AXObserver — публичный механизм уведомлений ([Apple](https://developer.apple.com/documentation/applicationservices/1460133-axobservercreate)); некоторые целевые приложения могут не поддерживать отдельные notifications, поэтому fallback нужен. Timeout настраивается через [AXUIElementSetMessagingTimeout](https://developer.apple.com/documentation/applicationservices/1459345-axuielementsetmessagingtimeout).

Оптимизировать после исправления возврата окна. Для подтверждения выигрыша сравнить CPU, wakeups, число AX запросов, p50/p95 задержки reveal/hide и пропуски кадров до/после на одном наборе приложений. В текущем аудите эти показатели не измерялись. Отдельно добавить Reduce Motion; анимация чужого окна через AX не превращается в обычную Core Animation-анимацию локального NSView.

## 6. Сборка и качество репозитория

- `xcodebuild build` Debug и Release: **PASS**. `xcodebuild analyze`: **PASS**. Анализатор не проверяет перечисленные последовательности событий Swift-менеджера.
- `xcodebuild test`: **не настроен**, exit 66: `Scheme SlideOverTahoe is not currently configured for the test action.` В shared scheme нет тестовых targets.
- Предупреждения исходников: deprecated `onChange(of:perform:)` в `SettingsView.swift:50`, unused `s` в `SlideOverManager.swift:302`. Предупреждение AppIntents metadata без зависимости — служебное, не дефект управления окнами. Сообщения CoreSimulator/LaunchServices в sandbox не помешали macOS-сборкам.
- Scheme Run использует Release; для обычной отладки разумно Debug. Release оставлять для профилирования и проверки выпуска.
- Deployment target на уровне project 26.2, на уровне target 26.0; реально используется 26.0. Унифицировать и тестировать выбранный минимум.
- В Git отслеживаются `xcuserdata`; отсутствовали `.gitignore`, README, архитектурная документация и CI. Документация добавлена этим аудитом; удаление пользовательских Xcode-настроек из истории и настройка CI пока только предлагаются.
- AppIcon содержит placeholders без файлов изображений. UI смешивает русские/английские подписи; нет ресурсов локализации. Меню `rightToggleItem` обновляется только при клике в самом меню, поэтому изменение toggle в настройках может оставить устаревшую галочку.
- `NSScreen.main!` — потенциальная авария при отсутствии доступного экрана; нужна безопасная ветка. Неиспользуемые `originalFrame`, `lastActivatedPID`, поле `trackingArea` усложняют чтение. `NSLock` в реестре удерживается во время restore/AX IPC: лучше получить снимок ссылок под lock и выполнять внешние операции после освобождения, либо придерживаться main actor без смешанной модели блокировок.

## 7. Выполненные тесты и воспроизведение

```sh
bash scripts/run-audit-tests.sh
```

Скрипт создаёт временный каталог, компилирует тестовый executable с исходниками менеджера, запускает и удаляет executable/cache. Требуется macOS с Xcode/Swift, используются AppKit, NSWorkspace и RunLoop. Тестовый AX-backend проверяет вызовы production-кода, но принимает положения, которые реальное приложение может ограничить. Он не является UI-тестом и не симулирует весь WindowServer.

Ожидаемый результат на базе аудита:

```text
PASS baseline: dock writes an off-screen position
PASS baseline: ordinary restore returns the original window
FAIL A01: repeated hide preserves restore position
FAIL A02: replacing target restores the old window
FAIL A03: restore cancels queued hide animation
FAIL A04: reversing animation preserves visible destination
FAIL A05: failed AX move must not report hidden
FAIL A06: changing grip updates actual docking geometry
PASS baseline: missing settings decode with defaults
FAIL A07: persisted settings validate numeric bounds
FAIL A08: failed restore retains recovery information
FAIL A09: disabling inactivity cancels an already scheduled hide
3/12 passed; 9 failed
```

Exit code 1 сохраняет обнаруженные ошибки видимыми. После исправлений соответствующие сценарии должны стать PASS. Не подменять ожидания «текущим неправильным поведением». Далее вынести AX boundary в production-протокол и перенести harness в обычный test target с fake clock для устранения зависимости от реального времени.

Команды проверки проекта (заменить Debug на Release для второй сборки):

## 9. Рекомендуемая последовательность работ

1. **Возврат окна и переходы состояния:** A01–A05, A08–A09, B03/B04; единая отмена действий, ошибки AX, аварийная команда возврата. Добиться PASS соответствующих тестов.
2. **Выбор окна и геометрия:** B01/B02, A06/A07, lifecycle observers, понятные ограничения нескольких дисплеев/fullscreen. Подключать picker после укрепления восстановления.
3. **Профилирование и оптимизация:** кеш hit testing, AXObserver, timeout, ограничение событий и отменяемая анимация; измерить результат.
4. **Качество выпуска:** test target/CI, Debug scheme, меню/доступность/иконка, Hardened Runtime, подпись, notarization; затем актуализировать `main`.

Первоочередная цель следующей доработки: выбранное окно всегда можно вернуть, даже при быстрой смене команд и ошибке Accessibility. До этого косметическая полировка ручки даёт меньшую пользу, чем устранение подтверждённых дефектов.
